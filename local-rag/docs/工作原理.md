# Local RAG 完整工作原理

本文说明 **本仓库 `local-rag` 的真实实现**，不是泛泛的 RAG 概念介绍。

---

## 1. 一句话定义

**RAG（Retrieval-Augmented Generation）** = 先从本地文档里找出和问题最相关的若干片段，再把这些片段连同问题交给大模型生成答案。

本系统把这件事拆成两条主链路：

1. **离线建库（Ingest / Index）**：文档 → 切片 → 向量 → 落盘索引  
2. **在线问答（Retrieve / Generate）**：问题 → 向量 → 检索 Top-K → 拼 Prompt → LLM 回答

```
┌─────────────── 离线建库 ───────────────┐
│  docs/*.md|txt|pdf                     │
│       ↓ 读文件 / 抽文本                 │
│  文本切片 Chunk（约 600 字，重叠 100）   │
│       ↓ Embedding 模型（本地）          │
│  向量矩阵 + chunks.json 写入 data/index │
└────────────────────────────────────────┘

┌─────────────── 在线问答 ───────────────┐
│  用户问题                                │
│       ↓ 同一套 Embedding 模型           │
│  与索引向量做余弦相似度，取 Top-K         │
│       ↓ 拼「资料 + 问题」Prompt          │
│  OpenAI 兼容 API（DeepSeek / Ollama…）  │
│       ↓                                 │
│  答案 + 引用片段（citations）            │
└────────────────────────────────────────┘
```

## 2. 模块与目录职责

| 路径 | 作用 |
|------|------|
| `data/docs/` | 原始文档存放处（上传也会写到这里） |
| `data/index/` | 向量索引与切片元数据 |
| `src/ingest.py` | 读文件、规范化、切分、生成 `Chunk` |
| `src/embed.py` | 本地 `sentence-transformers` 嵌入 |
| `src/store.py` | numpy 向量库读写与检索 |
| `src/llm.py` | 调用 OpenAI 兼容聊天接口 |
| `src/rag.py` | 编排：重建索引 / 问答 |
| `src/config.py` | 路径、LLM 配置、RAG 超参 |
| `src/app.py` | FastAPI：上传、删文档、建索引、提问 |
| `static/` | 浏览器 UI |

## 3. 离线建库：从文档到索引

入口：`rag.rebuild_index()`（UI「重建索引」或 `POST /api/reindex`）。

### 3.1 收集文档

`list_docs(data/docs)` 扫描目录，只接受：

- `.txt`
- `.md` / `.markdown`
- `.pdf`

### 3.2 读取文本

- txt/md：按 UTF-8 读全文（非法字节替换）  
- pdf：用 `pypdf` 逐页 `extract_text()` 后拼接  

> 注意：扫描版 PDF（纯图片）抽不出字，需要 OCR（本系统未做）。

### 3.3 文本规范化

`_normalize()` 做简单清洗：统一换行、压缩多余空行。

### 3.4 切片（Chunking）

默认参数（可在 `llm_config.json` 的 `rag` 字段改）：

- `chunk_size = 600`：每段目标长度（字符）  
- `chunk_overlap = 100`：相邻段重叠，减少“答案被切断”

切分策略（`split_text`）：

1. 按窗口向前切  
2. 若未到文末，尽量在窗口内找最近的 `\n\n` / `。` / `\n` 作为断点  
3. 下一段起点回退 `overlap` 字符  

每个切片变成一个 `Chunk`：

```text
id          = "文件名#序号"     例如 rag-intro.md#0
text        = 切片正文
source      = 文件名
chunk_index = 该文件内第几段
```

### 3.5 嵌入（Embedding）

`embed_texts(所有切片文本, embedding_model)`：

- 默认模型：`sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`  
- 本地加载（首次会下载模型权重）  
- `normalize_embeddings=True`：向量做 L2 归一化  

归一化后，两个向量的**点积 = 余弦相似度**，检索时可直接用矩阵乘法。

### 3.6 落盘索引

`VectorStore.save()` 写出三份文件：

| 文件 | 内容 |
|------|------|
| `data/index/chunks.json` | 全部切片元数据（含正文） |
| `data/index/vectors.npy` | shape = `[N, D]` 的 float32 矩阵 |
| `data/index/info.json` | 嵌入模型名、片段数、维度 |

**重要：** 重建索引是**全量重建**（读 docs 下全部文件重算），不是增量更新。删文档后也需要再点一次「重建索引」才会从向量库消失。

## 4. 在线问答：从问题到答案

入口：`rag.ask(question)`（UI「提问」或 `POST /api/ask`）。

### 4.1 前置检查

- 问题非空  
- 索引已存在且 `chunks` 非空，否则报错提示先建索引  

### 4.2 问题向量化

用**建库时同一套**嵌入模型：`embed_query(question)`。  
若用不同模型，向量空间不一致，检索会失效。

### 4.3 相似度检索

`VectorStore.search(query_vec, top_k)`：

1. `scores = vectors @ query_vec`（逐行点积）  
2. 取分数最高的 `top_k`（默认 4）  
3. 返回 `[(Chunk, score), ...]`  

这是**暴力检索**（线性扫描全部向量）。文档量到数万段仍通常够用；更大规模才需要 FAISS/HNSW 等近似近邻。

### 4.4 拼装 Prompt

系统提示固定为：

> 只根据给定资料回答；资料不足要说「资料中未找到」；可引用 `[资料1]`。

用户消息结构：

```text
资料：
[资料1 | 文件名 | 相关度 0.xxx]
……切片正文……

[资料2 | …]
…

问题：用户的问题
```

同时组装 `citations` 返回给前端展示（来源、分数、原文片段）。

### 4.5 LLM 生成

`llm.chat(messages)`：

- 读 `llm_config.json`（或环境变量覆盖）  
- 走 OpenAI SDK，`base_url` 可指向 DeepSeek、Ollama 等兼容服务  
- 返回模型文本作为 `answer`  

**检索在本地完成；生成默认走远端/本机 API。**  
嵌入模型本地，聊天模型按配置，两者职责分离。

## 5. Web 请求如何串起来

| API | 行为 |
|-----|------|
| `POST /api/upload` | 文件写入 `data/docs/`（不自动建索引） |
| `DELETE /api/docs/{name}` | 删除 docs 中文件（需再重建索引） |
| `POST /api/reindex` | 全量：读 docs → 切片 → 嵌入 → 覆盖 index |
| `POST /api/ask` | 检索 + 调 LLM → `{answer, citations}` |
| `GET /api/status` | 文档列表、片段数、LLM/嵌入状态 |

前端流程：上传 → 重建索引 → 提问 → 展示答案与引用。

---

## 6. 为什么这样设计（取舍）

| 设计点 | 原因 |
|--------|------|
| 切片 + 检索 | 避免整库塞进上下文，成本低、可溯源 |
| 本地 Embedding | 不依赖云端嵌入接口，隐私更好 |
| numpy 向量库 | 依赖少、易调试；够用小中规模知识库 |
| 重叠切片 | 降低关键句落在边界外的概率 |
| 强制“只根据资料答” | 降低幻觉，符合知识库问答预期 |
| 重建而非增量 | 实现简单可靠；文档量不大时足够 |

## 7. 数据流示例

假设 `data/docs/rag-intro.md` 只有一段说明「什么是 RAG」。

**建库：**

1. 读出全文 → 1 个 Chunk `rag-intro.md#0`  
2. 嵌入得到 1 条向量，写入 `vectors.npy`  

**提问「什么是 RAG？」：**

1. 问题向量化  
2. 与唯一片段相似度很高，作为 `[资料1]`  
3. Prompt 带上该段文字发给 LLM  
4. 模型基于资料概括回答，前端同时显示引用原文  

---

## 8. 常见边界与局限

1. **没建索引就提问** → 直接报错  
2. **上传后未重建** → 旧索引不含新文件  
3. **PDF 无文字层** → 切片为空或很少  
4. **相关度低的 Top-K 仍会送进 Prompt** → 模型可能被噪声干扰（可调高阈值过滤，当前未做）  
5. **LLM 未配置** → 检索仍可做，但生成失败  
6. **换嵌入模型后** → 必须重建索引

## 9. 可调参数（`llm_config.json` → `rag`）

```json
{
  "rag": {
    "chunk_size": 600,
    "chunk_overlap": 100,
    "top_k": 4,
    "embedding_model": "sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2"
  }
}
```

- `chunk_size` 更大：上下文更完整，但检索更“粗”  
- `overlap` 更大：边界更稳，索引更大  
- `top_k` 更大：资料更全，噪声与 Token 成本也更高  

---

## 10. 总结

本 Local RAG 的本质是：

> **用本地向量检索给 LLM 喂“临时开卷资料”，让回答有据可查。**

- **懂什么**：`data/docs` 里你放进去、并成功写入索引的内容  
- **怎么找**：同一嵌入空间下的余弦相似度 Top-K  
- **怎么答**：资料约束下的 LLM 生成，并回传引用片段  

理解以上两条链路（建库 / 问答），就理解了本系统的全部工作原理。
